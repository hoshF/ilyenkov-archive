# 校阅记录

本书成书之后发现的问题，逐条记在这里。**系列里每本书各有一份**，见
[`template/README.md`](template/README.md)。

## 收什么、不收什么

**只收译文内容的问题**：漏译、误译、术语不统一、注记归类、底本疑点。

**版式的事不收**，归 [`template/TYPESETTING.md`](template/TYPESETTING.md)——字号、行距、
断行、书眉、标题、强调怎么排、署名与著录怎么排，都在那里。两者的分界是：**改译文的进这里**
（要重置审校、重签字），**改模板的不进**（译文一个字不动，重编译即可）。

## 怎么用

**发现问题不必立即改、更不必立即编译。** 记进「待改」，攒够一批一起改、一起走流程、
一起编译一次。这是校阅的原则：修正就是修正，不搬家、不复杂化，但也不要改一处编一次。

**定位一律用锚点 `chNNN-pNNNN`，不用页码。** 每次重编译页码都会变，按页码记的东西
下一版就对不上了；锚点是译文块的身份，不随排版动。要在 PDF 里找某一条，拿锚点对应的
中文去搜。`scripts/read_pdf_notes.py` 把 PDF 上的划线批注直接读成锚点，不必人工换算。

**「不改」也要记，而且理由最值钱。** 机器通查会反复报出同样的东西；判过一次而不写下来，
下一个人（或下一次的自己）还要从头查一遍。

## 修正的固定路径

改一处译文，连锁的步骤是固定的：

1. 改 `units/chNNN/final.md`——**只改定稿**，`literal.md` 是起草阶段的快照，不动
2. **在该单元 `issues.md` 补一节 `## 补记（日期　缘由）`**，写明改了哪一块、依据什么、
   由谁报出——这是**单元自己的**记录，本文件是全书的账，两者都要有。
   `issues.md` 在**准确性**哈希范围内（连同原文映射与 `literal.md`），补记会使它失配，
   须与第 3 步一起重取；语言哈希只覆盖 `final.md`，不受影响
3. 把该单元两道审校重置为 `pending`、状态退回 `accuracy_review`
4. 所有者审阅认可后，`check_translations.py --review-hashes <项目目录>` 重取哈希并填回
5. `updated_at` 不得早于审校日期，须一并更新
6. `build_merged_translation.py` 重生成合并本——**它是派生物，不重生成就旧了**
7. 全批改完后才 `build_book.py` 出 PDF

> 第 2–5 步现在全靠手改 `translation.json`，字段名必须一字不差
> （`reviewed_at`／`scope_sha256`，不是 `date`／`hash`）。这一批三次修订里错过两轮，
> 都靠校验器拦下。**值得做成一条命令**，见本文件末「余留的改进」。

**修正期间项目留在原地，不退回 `drafts/`。** `check_translations.py` 会报
「reviewed/ requires every unit status=reviewed」——**那是过渡态，是对的**，它在说签字还没
回来。一批改完、签字填回，它自己就通。不要为了让中间态好看去改规则或加状态，
那等于削弱这道把关。

**重编译会让页码全变**：上一版按页码记的批注一律失效，须换新版重批。

## 余留的改进

**修订路径没有工具。** `check_translations.py` 只有 `--check`／`--inspect-source`／
`--review-hashes`／`--status` 四个命令，重置与回填签字全靠手改 JSON。2026-07-30 这一批
三次修订中错过两轮（字段名写成 `date`／`hash`；漏更 `updated_at`），均由校验器拦下——
**校验是有效的，但它拦的是本不该发生的错**。

建议加 `--revise <项目> <单元>`：重置两道审校为 `pending`、状态退回 `accuracy_review`、
并提示去补 `issues.md`；再加 `--sign <项目> <单元>`：重取哈希、填回签字、同步 `updated_at`，
并在输出中打印「此为代填，效力来自所有者审阅」。
